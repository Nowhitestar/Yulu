<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Installer scripts → user's launchd/PATH | The decomposed scripts write LaunchAgent plists with a substituted PATH; a wrong PATH can run an unexpected node/python binary. |
| `brew install` → host package manager | setup_deps mutates the host's Homebrew state. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-03 | Elevation of Privilege | `install_plist` PATH substitution | mitigate | `launch_path` hardcodes a stable, well-known prefix order (`~/.local/bin:/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin`) instead of an attacker-influenceable nvm-versioned literal (§6b fix); no untrusted dir is prepended. |
| T-01-04 | Tampering | `brew install` in setup_deps | accept | Reuse-first is enforced later (Phase 5 REUSE); Phase 1 keeps the existing explicit formula list (no arbitrary/remote formula); auto-installing Homebrew without consent is out of scope per REQUIREMENTS. Low risk — same formulae as today. |
| T-01-05 | Denial of Service | `set -u` on unbound monolith globals | mitigate | Pitfall 5 audit: every concern script takes state via args/env with `${VAR:-default}`, so standalone invocation cannot crash on an unbound global that the monolith tolerated. |
| T-01-SC | Tampering | npm/pip/cargo installs | mitigate | `setup_ui.sh` runs `npm ci` against the COMMITTED `package-lock.json` (not `npm install`), so the dependency set is pinned by the lockfile; no new package added this phase. brew uses an explicit formula list. No `[ASSUMED]`/`[SUS]` language package introduced. |
</threat_model>
