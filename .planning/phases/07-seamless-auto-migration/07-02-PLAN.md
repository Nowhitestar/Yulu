<objective>
Build the migration recording-guard (D-02, MIG-02): before stopping ANY daemon, `migrate/guard.py` checks whether a recording is active by querying the audio_daemon status socket (the canonical "is recording" arbiter, exactly as `record_audio._raise_if_daemon_recording` does) and REFUSES to stop while active — raising `RecordingActive` instead of truncating an in-flight capture. When no recording is active, it stops daemons through the Phase 2 `MacOSDaemonManager.unload()` clean-stop (`launchctl unload`), with NO `pkill -9` anywhere — the `open -W` orphan that historically forced `pkill` is gone (D-06).

Purpose: This is THE data-loss prevention for the phase. A migration that stops the audio daemon mid-recording truncates the WAV (CONCERNS §2d). The guard makes that impossible by deferring to the daemon's own recording flag and refusing rather than forcing.

Output: `migrate/guard.py` + `tests/test_migrate_recording_guard.py` (Wave 0 for this plan). File-disjoint from Plan 01 -> runs in the same wave.
</objective>

The flock itself is held only for the ~50ms start handshake, so DO NOT try to acquire the flock to detect recording — the daemon socket is the arbiter (this is exactly why `_raise_if_daemon_recording` exists).
- `MacOSDaemonManager` (Phase 2): `unload(name: str)` runs `launchctl unload <plist>` (list-form subprocess, no shell, no pkill); `status(name) -> "running"|"stopped"|"unknown"`. Instantiate it directly (`MacOSDaemonManager()`) — the proven idiom; do NOT route through a non-existent `get_platform()` accessor (it is referenced only inside a degrading try/except in state.py and is not defined in `yulu_platform/__init__.py`).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| in-flight recording (a live capture writing a WAV) -> migration's daemon-stop | Stopping the audio daemon mid-recording truncates/corrupts the capture. The recording-guard is the boundary control: migration may not cross it while a recording is active. |
| daemon supervision (launchctl) -> migration | Migration must stop daemons cleanly; a forced kill (`pkill -9`) is the historical truncation vector (CONCERNS §2d). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-04 | Tampering (data-integrity, HIGH) | stop_daemons_guarded truncating a live WAV | mitigate | Guard queries the audio_daemon status arbiter FIRST and raises `RecordingActive` (refuse) when recording — `manager.unload` is never reached. Proven by a test asserting unload call-count 0 while recording. This is the headline MIG-02 control. |
| T-07-05 | Tampering (data-integrity, HIGH) | a `pkill -9` reintroducing the truncation vector | mitigate | The module uses `MacOSDaemonManager.unload` (clean `launchctl unload`) exclusively; a static source grep asserts ZERO `pkill` occurrences. The Phase 2 direct-launch fix (D-06) removed the orphan that forced pkill, so clean-stop suffices. |
| T-07-06 | Denial of Service | a hung/absent socket blocking the guard forever | mitigate | `socket_send` uses a 5s socket timeout (record_audio line 97) and returns None on any error -> `recording_active` degrades to False; the guard never blocks indefinitely. (A down daemon is, correctly, not recording.) |
| T-07-07 | Spoofing | a stale `.recording.lock` falsely claiming a recording | accept | The lock metadata only ENRICHES the refusal message; the AUTHORITATIVE recording signal is the live daemon socket, not the persisted lock file. A stale lock cannot itself trigger a refusal (recording_active ignores it). |
</threat_model>
