<objective>
Create `provision/attest.py`: the fail-closed asset-integrity gate — the headline supply-chain control of this phase (PROV-03, ASVS V10). It implements the gh-auth fallback LADDER discovered live in research: `gh attestation verify`==0 -> PASS; `gh` exit-4 (unauthenticated, the public-repo limitation cli/cli #11803) OR `gh` absent -> SHA-256 `checksums.txt` floor; a non-4 nonzero on an authed `gh` -> corroborate-with-checksum-or-REJECT. Any integrity failure raises `TamperError` BEFORE any step's `apply()` runs (fail-closed). Checksum verification REUSES `release_installer.verify_checksum`/`parse_checksums` — never a fresh crypto loop. A `checkpoint:human-verify` closes the two checks that genuinely need a real published release asset + gh auth (real verify + signer-workflow strictness, RESEARCH A1/Q2).

Purpose: PROV-03 requires `gh attestation verify` before execution with the signed-zip path as a non-negotiable fallback; PROV-02's spike exit criterion (2) is tampered-asset rejection. Per D-03 a tampered asset is rejected before any step (fail-closed). RESEARCH Pitfall 1 is decisive: gating on `command -v gh` alone is wrong because an unauthenticated gh exit-4s on every verify.
Output: `provision/attest.py`, Wave-0 test `tests/test_provision_attest.py`, and the real-asset human-verify checkpoint.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| network/release host -> downloaded zip | The release asset is untrusted until verified (MITM / compromised-release tampering) |
| `gh` auth state -> gate decision | An unauthenticated gh (exit-4) must NOT be misread as a verify failure (would DoS install); it degrades to the checksum floor |
| verified asset -> step.apply() | No `apply()` may run until verify_asset returns PASS (fail-closed, gate is FIRST) |
