<objective>
Wire the three Wave-1 modules into the user-facing surface and decouple skill install. Create `provision/cli.py` (argparse: `provision [<step>]`, `provision --all [--asset <zip> --checksums <txt>]`, `skill install [--agent <name>]`) which is the resume-walk DRIVER composing registry + state + attest: when an asset is supplied the attest gate runs FIRST (fail-closed) before any `apply()`; the walk marks each step `running` before `apply()` and the result after, skipping steps already `ok`. Create `provision/skill.py` by lifting `setup.sh:install_agent_skill` (lines 620-676) minus the interactive prompts into an idempotent, non-fatal `npx skills add` wrapper. Wire `provision` + `skill` subcommands into the `yulu` bash dispatcher. Decouple: REMOVE the `install_agent_skill` call from `setup.sh`'s main flow (line 925).

Purpose: PROV-01 requires `yulu provision <step>`; PROV-05 requires `yulu skill install [--agent]` decoupled from `setup.sh` and idempotent; PROV-02's spike is the dual-caller resume walk end-to-end. Per D-02 the host agent CAN drive `yulu provision`, but the signed-zip + curl|bash path stays PRIMARY (this plan adds the agent-drivable CLI, it does NOT replace install.sh). Per D-05/D-08 skill install is extracted and removed from the core flow. Idempotency of `npx skills add` is the Yulu wrapper's job (RESEARCH Pitfall 4).
Output: `provision/cli.py`, `provision/skill.py`, edited `yulu` + `setup.sh`, and Wave-0 tests `tests/test_provision_cli.py` + `tests/test_provision_skill.py`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller -> `yulu provision`/`yulu skill` | Subcommand args (step name, agent names, asset path) are untrusted; resolve to fixed steps / argv-list calls only |
| `provision --all --asset` -> step execution | The attest gate MUST run and PASS before any step.apply() (fail-closed, the gate is the FIRST thing the walk does when an asset is present) |
| skill install -> npx | npx is invoked with an argv list over a fixed repo dir + agent names; no arbitrary package, no shell interpolation |

## STRIDE Threat Register (ASVS L1 + V10 supply-chain)

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-15 | Tampering | gate bypass in the walk | mitigate | provision --all calls attest.verify_asset FIRST when --asset is supplied and aborts on TamperError before any apply() — the cli gate-before-apply test asserts no step runs on a tampered asset (fail-closed). Block on high. |
| T-06-16 | Injection | provision <step> arbitrary execution | mitigate | the step arg resolves via step_by_name against the fixed REGISTRY; an unknown name errors (no arbitrary script path executes); subprocess uses argv lists |
| T-06-17 | Injection | skill install -> npx | mitigate | skill_install builds an argv list (`npx -y skills add <repo_dir> -g -a <agent> -y`); repo_dir is the fixed repo root, agent names are passed as separate argv elements (no shell=True, no metachar exposure) — no arbitrary package install |
| T-06-18 | Tampering | resume duplicates daemons | mitigate | the walk uses state.py running-before-apply/ok-after + step.check() idempotency so a re-run after a kill loads no duplicate daemons (composes Plan 02's guarantee) |
| T-06-19 | DoS | skill/npx failure aborts install | accept->mitigate | skill install is decoupled and non-fatal (returns 0 on npx-absent/failure) so it can never break the core install path (D-05: independent of core install) |
</threat_model>
